# API architecture

The product API is a contract-first Effect HttpApi (`effect/http-api`) under `/api/v1`, inside an Alchemy Effect-native Cloudflare Worker (`apps/server/src/worker.ts`). Effect owns the transport and application execution. Each of the 49 procedures is an HTTP endpoint with its own method and path; callers use its typed group and endpoint (`api.people.planWindowHistory({ payload })`). Better Auth remains an ordinary HTTP handler on the same Effect `HttpRouter`, because it defines its own protocol and routes.

## Package boundaries

- `packages/contracts` contains the browser-safe API contracts (`src/http/`). Each endpoint is declared once, with `read` (GET), `read.post` (a read whose input can outgrow a URL), or `write.post`, `write.put`, `write.patch`, `write.delete` (`endpoint.ts`), inside its namespace's `planningCenterGroup` or `plainGroup` (`group.ts`), which fixes the middleware order and gives the server group, the client's wire group, and the namespace's routes. `api.ts` composes `ProductApi`, `ProductWireApi`, and `procedureRoutes`, the one route table (tag to method, path, path params, where the rest of the input travels, kind, flag, Planning Center access) that the client, the server's unknown-path answer, fixture transports, and the contract test read. It also holds the product fault classes (`src/faults/`), shared by server and client. Its Effect schemas are the only definition of each shape: the browser saves cached answers through the endpoint's success schema (`apps/web/src/lib/stored-json.ts`, `Schema.toCodecJson`) and drops any saved answer that no longer decodes, as the Expo app does (`apps/mobile/src/app-shell/query-persistence.ts`). It must not import database, auth, or framework modules.
- `packages/planning-center-models` contains shared Planning Center data shapes plus pure calendar and scheduling rules. It is browser-safe and framework-independent.
- `packages/presentation-mode` contains the server-side presentation-mode guard, seed, and cache namespace shared by the API and the web build, which inlines the namespace.
- `packages/api` contains server-side application programs, typed faults, explicit feature modules, Better Auth and database integration, Planning Center adapters, and the API server (`src/http/`: the `ProcedureScope` and `PlanningCenterSession` middleware, outcome logging, the unknown-path answer, and `handlers/`, one `handle` line per endpoint).
- `apps/server` is the API Worker. It reads its settings with `Config` at startup and binds D1, the Planning Center cache KV namespace, and the iOS update bucket (R2, read-only). It builds its one Effect `HttpRouter` (`http-app.ts`: the API, Better Auth, the iOS over-the-air update routes, liveness) in its constructor, before any request, and the server dependencies on the first request (bindings are readable only inside one), handing them to every request as `IsolateServer`. Around the router, from the outside in: `Cache-Control: private, no-store` and the release header on every answer (preflights and unknown paths included), one CORS policy (`cors.ts`: the product origin only, with credentials, allowing the headers the clients send and exposing `Retry-After` and the release header), and the disconnect wrapper (`disconnect.ts`).
- `packages/client` is the one product client (`makeProductClient`, over `HttpApiClient.make(ProductWireApi)`) for web, SSR, Expo, and the deploy check, plus `failureStatus`, the request scheduler, and the TanStack Query helpers. `client.run((api) => api.<group>.<endpoint>({ params, query, payload }), options)` runs the native client Effect and preserves decoded fault classes. HttpApiClient in the installed Effect version names URL parameters `query`. The HttpClient adds priority, version, bearer, account, and demo headers centrally. `callForQuery(context, client, (api) => api.people.search({ query }))` supplies the abort signal and current read priority, with write endpoints excluded from its callback type. TanStack Query, persistence, and the scheduler remain.
- `apps/web` calls the API through one `productClient` per tab (`src/product-client.ts`) and, during SSR, one client per call over the API service binding (`src/server/server-api.ts`). It owns browser caches, hydration, navigation, and presentation helpers under `src/lib`. It must not import server-side modules from `packages/api`.

## Request flow

```text
apps/web
  -> productClient.run((api) => api.people.search({ query }))
  -> apps/server <method> /api/v1/<path>
  -> ProcedureScope and PlanningCenterSession middleware
  -> packages/api/src/http/handlers
  -> Effect application program
  -> packages/api feature module
  -> Planning Center or database adapter
```

The Worker builds `ServerDependencies` (`packages/api/src/server.ts`: the typed `ServerConfig`, the Drizzle database, Better Auth, the feature flag client, the Planning Center read caches, and the feature-module read caches) once per isolate. The Worker's construction phase acquires the D1, KV, and Cloudflare Flagship bindings, as `Cloudflare.D1.QueryDatabase`, `Cloudflare.KV.ReadWriteNamespace`, and `Cloudflare.Flagship.ReadFlags`, and passes the raw bindings in. Programs evaluate flags per request with `featureFlags.isEnabled(name, subject)`, never from configuration; see [Feature flags](environment.md#feature-flags). Each request brings them as the `IsolateServer` service, and `ProcedureScope` provides them to every procedure as the `Server` service; `packages/api` never reads `process.env` or `cloudflare:workers`. Procedures run on the Worker's own request fiber, so handlers inherit its HTTP client, logger, and the per-invocation tracer from `Cloudflare.Telemetry()`, and `ProcedureScope` adds the isolate's Planning Center pacer. The router is built from nothing but the isolate's scope: `HttpApiBuilder.group` captures the services of the fiber that builds it and gives them to every handler, so anything request-scoped it could see (an invocation's HTTP client, tracer, or execution context) would serve later requests, which workerd answers by hanging them. `ProcedureScope` reads the request's own HTTP client and `IsolateServer` from the request fiber (`fromRequestFiber`, the only untyped reads) and runs each procedure in a span named `api.<procedure>`, so each appears in the invocation's Workers trace beside its fetch, D1, and KV subrequests. It also provides a new `RequestContext` per procedure, built from the HTTP request (request ID, cloned headers, method, URL, user-agent metadata, and abort signal). Credentials and other identity-sensitive values belong in request-scoped services; they must not be captured by a process-scoped layer or implicit async context. Planning Center clients bind one explicit credential to both their Authorization header and cache scope for their entire lifetime. A [demo session](demo.md) resolves to the demo credential through a read-only client that rejects writes before they leave the process, and always presents people with fictional details.

Application programs fail with product faults (`packages/contracts/src/faults/`) rather than HTTP statuses, and the same classes reach the client, which rejects with them, so callers use `instanceof` or `failureStatus(error)`. `faultOutcome` maps each fault to its HTTP status and stable code once (Unauthenticated 401, Forbidden 403, InvalidInput and RequestRejected 400, ClientOutdated 426, NotFound 404, Conflict, AlreadyScheduled, and PositionMismatch 409, RateLimited 429, ExternalServiceFailure 502, PersistenceFailure and InternalError 500); each fault class carries its status as HttpApi's `httpApiStatus`, so the server answers with it and the client decodes the body back into the class by status. Every endpoint declares every fault until programs narrow their failures. Params, query, or a body that do not decode answer `RequestRejected` (`invalid-payload`); a body HttpApi cannot read at all (not JSON, 415 from the framework) answers `RequestRejected` (`malformed-request`), so every non-2xx answer is a declared fault and its outcome line logs the status sent. A path under `/api/v1` that names no endpoint answers `RequestRejected` (`unknown-endpoint`, 400), never `NotFound` (which SSR renders as a missing page); a known path with another method answers the same declared fault at 405 with `Allow`. Both are logged like matched calls, with no procedure: unknown paths log the requested path, and wrong methods log the known route template. One ordering differs from a validate-first transport and is accepted: HttpApi decodes inside its middleware, so a signed-out malformed request answers 401, and a malformed request to a flag-off endpoint answers 404, before 400. Planning Center HTTP, network, and malformed-response errors are classified at the provider boundary; unexpected adapter errors remain Effect defects. Defects and persistence failures are returned as opaque internal errors, with their original cause retained only for server-side logging.

Every response is marked `Cache-Control: private, no-store`, and `ProcedureScope` writes each cookie a procedure set (`ResponseCookies`, such as account selection) as its own `Set-Cookie` line and `Retry-After` on a rate-limited answer. Every client sends `x-pcobooster-client: <web|ssr|expo|deploy>;api=<N>` (`formatClientHeader`; `makeProductClient` always does); the server logs it and answers `ClientOutdated` (426) to a call without it, with one it cannot read, or below `MINIMUM_API_VERSION`. The URL's `v1` is the breaking version; `api=<N>` orders releases inside it.

Paths follow the resource: reads are `GET` with ids in the path and the rest in the query (scalars and scalar arrays as ordinary params), except the two reads whose cursors can outgrow Cloudflare's 16 KB URL limit, `POST /people/plan-window-history` and `POST /plans/:planId/candidate-details`, which are still reads in every other way. Writes use `POST` (create or act), `PUT` (set), `PATCH` (change part), or `DELETE` (remove, any context in the query).

When a caller disconnects (`disconnect.ts`), its call runs on its own fiber, raced against the request's abort signal: a read is interrupted, a write finishes because `ProcedureScope` runs writes uninterruptibly, and `waitUntil` (`Cloudflare.WorkerExecutionContext`) keeps the invocation alive until it has, so its outcome line and audit row record what Planning Center really did. The answer is a 499 no one receives.

## Native clients

Native clients call the same endpoints through `makeProductClient`, without cookies. It signs in through `GET /api/auth/native/start` and `POST /api/auth/native/exchange`, then authenticates with `Authorization: Bearer <signed session token>`, which Better Auth's `bearer` plugin turns into the session for every `auth.api.*` call, so procedures need no native-specific code. Where the browser sends a cookie, a native client sends a header: `x-pcobooster-account` for the selected organization (read before `pco-selected-account-id`) and `x-pcobooster-demo` for a demo session (read before `pcobooster-demo`). A bearer client never has a session cookie cache, so each procedure pays authoritative D1 session and user reads; see the dated [subrequest ledger](research/planning-center-rate-limits.md#2026-10-07-request-accounting-correction). See [Native app sign-in](native-auth.md) for the flow, the HTTP contract, error codes, and rollback.

## Planning Center adapters

The Planning Center client (`packages/api/src/planning-center/core-client.ts`), the services under `planning-center/services/`, and the feature modules under `modules/planning-center/` return Effects end to end. Their typed failure channel is `PlanningCenterError`: `PlanningCenterApiError` (an error status or unusable response), `PlanningCenterNetworkError` (fetch, body stream, or attempt timeout), `PlanningCenterReadOnlyError` (a blocked demo write), `PlanningCenterRateLimitError` (the credential's rate budget is spent for longer than the wait cap, so the request was not sent), and `PlanningCenterSubrequestLimitError` (Cloudflare refused the fetch with "Too many subrequests", or the procedure's request budget is spent). Application programs compose them directly and translate that channel once with `withPlanningCenterFaults`, which maps read-only writes to `Forbidden`, 429 responses and pacing rejections to `RateLimited` (with `retryAfterSeconds`), and subrequest limits and other provider failures to `ExternalServiceFailure`; anything else stays a defect.

- **Failure recovery.** A Planning Center failure never becomes empty or default data by accident. Code under `planning-center/` and `modules/` recovers only through `recoverPlanningCenterFailure` (`planning-center/recover-failure.ts`), naming the kinds it may fall back after: `not-found` (a 404), `provider-failure` (any other error status except 429, or a network failure), or `unusable-response` (a defect). Rate limits (`PlanningCenterRateLimitError` or a 429), subrequest limits (`PlanningCenterSubrequestLimitError`), read-only rejections, and interruption always propagate, whatever the caller lists. Each fallback logs its reason with the ids involved: `not-found` at `info`, anything else at `warn`. Code that needs a different recovery than a fallback value (the team positions series lookup) gates it with `isRecoverablePlanningCenterCause`. `lint/architecture-boundaries.test.ts` fails when an Effect recovery combinator appears in that code outside a short, justified list, and `testing/planning-center-failures.ts` lists the budget failures each recovery site is tested against. The remaining fallbacks:
  - Organization time zone: the configured `PLANNING_CENTER_TIME_ZONE` after a provider failure or unusable response, cached for 2 minutes.
  - A service type another organization owns (People dashboard activity, person detail): its schedules keep their plan dates, without rehearsal times.
  - A plan Planning Center does not find: no plan times.
  - A song never scheduled for the service type: no last scheduled item.
  - Deleting a plan time that is already gone: the delete succeeds.
  - Team positions: a failed service-type needed positions read tries the plan's series once.

  Everything else fails the procedure as a typed fault; progressive procedures return partial data only through their continuations (see [Progressive procedures](#progressive-procedures)), and the browser offers Retry.

- **Sparse fieldsets.** The heaviest reads ask Planning Center for only the fields this app reads (`fields[Type]=...`, `planning-center/sparse-fields.ts`): plan ranges and adjacent plans, plan rosters, the team directory, team position assignments, and a person's schedules. By default Planning Center computes every attribute, including counters such as a plan's `items_count` and a schedule's `position_display_times`; leaving them out returned the same values several times faster (a page of plans with `include=plan_times` went from about 2.5 s to 0.35 s). A fieldset also drops every relationship it does not name, and a field left out is missing for every reader and cache of that response, so add a field to its list before reading it.
- **Pages.** `fetchFirstPages` reads a collection's first page, and when that page reports `meta.total_count` and pages by 100, requests the pages after it together (six at a time, the Worker's open-connection limit) using Planning Center's own next link with only the offset changed; a collection that grew past its reported size is followed on by link. Page-by-page reads (`fetchPage`) stay sequential, since progressive procedures admit them one page at a time.
- **HTTP.** The client sends through an `effect/http` `HttpClient`. Alchemy's Worker runtime provides `FetchHttpClient` on the request fiber, `ProcedureScope` provides it to the procedure, `resolvePlanningCenterAccess` reads that client from context, and the request's services bind it together with the request credential for their lifetime. Tests pass an `HttpClient` over a scripted `fetch` (`testing/http-client.ts`).
- **Capabilities.** Each Planning Center capability is its own Effect service (`PlanningCenterPeople`, `PlanningCenterCatalog`, `PlanningCenterPlans`, `PlanningCenterPlanItems`, `PlanningCenterSongs`, `PlanningCenterProductAccess`, `OrganizationTimeZone`; `packages/api/src/application/planning-center/`). `provideAccess` binds every one to the request's resolved access, and `PlanningCenterAccess` itself carries only the credential's identity, cache scope, and presentation mode. An application program yields the capabilities it reads, so its requirement type names exactly those, and a test provides only what the program uses.
- **Retries and timeouts.** Only idempotent reads (GET and HEAD) retry, on a `Schedule` of at most two retries: 408, 429, 500, and 502 to 504 responses and attempt timeouts qualify; 429 waits for `Retry-After`, other responses back off 500 ms per retry, and timeouts 300 ms. An interactive read waits out a `Retry-After` of up to one Planning Center window (20 seconds), and a pacing rejection (`PlanningCenterRateLimitError`, `reason: "budget"`) the same way, since the pacer sent nothing: resending one request is cheaper than failing to the browser, whose retry reruns the whole procedure. A longer wait, and any wait over 5 seconds for a speculative read, fails at once (`RateLimited` with `retryAfterSeconds`) so the browser decides. A subrequest limit is never retried. Each attempt (pacing wait, request, and error body) has a 15 second Effect timeout, and the JSON body read uses what remains of that budget.
- **Pacing.** `PlanningCenterRatePacer` (`planning-center/rate-pacer.ts`) keeps one window per credential (cache scope) in the isolate, learned from each response's `X-PCO-API-Request-Rate-Limit`, `-Count`, and `-Period` headers; it never assumes 100 per 20 seconds. The Worker builds one pacer per isolate and `ProcedureScope` provides it to every procedure as the `PlanningCenterPacing` service, so every procedure for the same credential in the isolate shares it. Until half the reported limit is used (counting requests still in flight), reads go straight out. After that, each read takes the next slot, spaced `time left in the window / requests left`, so the remaining budget is spread across the window before sending rather than paused after the response. A 429 blocks the credential until its `Retry-After`, even when it is the first response the credential gets. At most 12 of a credential's requests are in flight from an isolate at once, across every procedure (`withSendPermit`); the rest wait for a permit after their pacing slot, so a plan page's fan-out commits fewer requests before rate headers that count other isolates and devices come back. A read whose slot is more than 5 seconds away fails with `PlanningCenterRateLimitError` (`reason: "budget"`) without being sent. Reads from a speculative procedure (see [Request priority](#request-priority)) never wait: they go out only while the window is below 40% of the reported limit, nothing is blocked by a 429, and no interactive read is waiting for a slot, and otherwise fail at once with `PlanningCenterRateLimitError` (`reason: "speculative"`), so the rest of every window stays for what the user is waiting on. Writes are counted but never delayed or rejected by the pacer, keep their no-retry rule, and still follow the provider-write boundary below. The pacer cannot see other isolates, tabs, or devices using the same Planning Center user; only a Durable Object per user could.
- **Request accounting.** `ProcedureScope` (`packages/api/src/http/procedure-scope.ts`) creates one `PlanningCenterRequestAccounting` per procedure call and provides it as `PlanningCenterAccounting`. The client counts each explicit API attempt (retries included), paced requests and their wait, 429s, pacing rejections, and subrequest-limit hits. It checks and charges the hard cap synchronously immediately before sending, after any pacing wait, so concurrent queued calls cannot overshoot it. A canceled wait releases its pacer reservation without consuming a request. API redirects are refused (`redirect: "manual"`): a 3xx fails as a typed provider response instead of following uncounted hops. Programs read the count with `planningCenterRequestsSpent` to return partial data. `PLANNING_CENTER_REQUEST_CAP` (40) is independent product policy, and `PROGRESSIVE_REQUEST_BUDGET` (36) is the planning target, not a second hard ceiling. The API Worker separately declares `limits.subrequests: 80` for the verified Workers Paid Standard account; that declaration needs deployment before platform enforcement exists. The [dated overhead ledger](research/planning-center-rate-limits.md#2026-10-07-request-accounting-correction) explains auth, D1, KV, flag, refresh, initialization and error-reporting overhead and its limits. After Cloudflare refuses one fetch, later requests in the same procedure fail without being sent. Direct core callers without accounting remain uncounted; standalone budgeted modules use `withPlanningCenterRequestCount` to create a fresh bounded 40-request accounting scope, preserving supplied transport accounting.

- **Logs.** Every pacing wait, pacing rejection, and 429 is logged at `info` with the endpoint (path and query parameter names only, never values, tokens, or bodies), method, attempt, wait or `Retry-After`, and the rate-limit headers. Cloudflare "Too many subrequests" refusals log at `warn`. Every procedure logs one line, message `rpc` (`packages/api/src/http/outcome.ts`), with the procedure (for example `people.planWindowHistory`), request ID, method, route template, status, code, duration, priority, client, the native release (`appRelease`, from `x-pcobooster-app`), kind, and its Planning Center counts: `info` below 500 (4xx, and 499 when the caller left), `error` with the cause from 500 up, which production also reports to PostHog. Lines are Effect logs (`moduleLog` in `packages/api/src/logging.ts`) whose fields become annotations, so each also carries the procedure and request ID that `ProcedureScope` annotates; tests capture them with `recordLogs` (`testing/logs.ts`). Code outside any Effect, such as Better Auth hooks, writes the same lines through `boundaryLog`.
- **Caches.** `cachedRead` (`planning-center/services/cached-read.ts`) adapts an Effect load to the request's view of a `PlanningCenterReadCache`. The load is built only on a miss and runs in its own fiber, so each caller waits independently. A load runs with the priority of the procedure that started it; an interactive caller that joined a speculative load the pacer held back loads again with its own priority rather than failing with the prefetch.

Cancellation is Effect interruption. A read runs in the request's fiber, which the transport interrupts when the Fetch request aborts; interrupting a Planning Center call aborts its in-flight fetch, pacing wait (releasing its slot), or pagination. Shared cache loads keep per-caller waiters: one disconnected caller does not cancel another, but the load is interrupted and its result is not cached when no callers remain. Reads that fall back after a failure (such as the organization time zone) still stop when interrupted. At the provider-write boundary, the application checks the request signal once more (`ensureRequestIsOpen`); writes run without request-driven interruption, so after a write starts, execution waits for the provider result and required invalidation or audit work instead of reporting a cancellation while a hidden write continues.

## Request priority

Every call from one person spends the same Planning Center budget, so the browser and the API both put what the user is waiting on ahead of work that only might be needed. `@pcobooster/contracts/request-priority` defines the two priorities:

- **Interactive:** data on screen, or what a click just asked for. The default.
- **Speculative:** loaded ahead of a likely next step: hover and focus prefetches, the Plan tab's items and the plan-window history while the positions list is on screen, and the Plan tab's song options.

In the browser, `productClient` (`apps/web/src/product-client.ts`) counts interactive calls in flight through the tab's request scheduler (`packages/client/src/request-scheduler.ts`), and every call sends its priority as the `x-pcobooster-priority` HTTP header. The query helper exposes only reads, including the two POST reads. The client and server force writes to interactive priority. Speculative tasks go through `requestScheduler.runSpeculative`: they run one at a time, in order, and each starts only once no interactive call has been in flight for 250 ms (long enough for the query the next render starts from a response, such as candidate details after candidates). A task whose page is left before its turn is dropped. `useIntentPrefetch` schedules every hover prefetch this way, and a newer intent replaces one still waiting. Prefetched queries are marked with `speculativeQuery`; their query functions call the product client through `callForQuery` (`packages/client/src/query.ts`), which sends speculative only while nothing on screen observes the query, and resends a held-back call as interactive when the user opened what was being prefetched.

On the API, `ProcedureScope` reads the header into the procedure's `PlanningCenterRequestAccounting` (`priority`), the procedure's outcome line logs it, and the pacer applies it (see Pacing above). A held-back speculative call maps to `RateLimited` like any pacing rejection; prefetches ignore it.

## Progressive procedures

Screens whose data would take more than one invocation's subrequests are split into small procedures the browser calls progressively. Each call plans against `PROGRESSIVE_REQUEST_BUDGET` (36: the cap less room for retries of reads it already admitted), admitting work by upper-bound costs and then counting what was really sent, so cached reads leave room for more work. Paginated Planning Center collections are read one page at a time and admitted page by page, never as one request. A procedure that cannot finish returns what it has and a continuation (`deferredPersonIds`, `deferredPlans`, `continuation`) holding the next page offsets and what earlier pages found, so a follow-up call resumes with fresh caches; the browser calls again with it. A collection read whole (`fetchAll`) fails with `PlanningCenterPaginationError` rather than return part of itself, reads that only need a collection's start use `fetchFirstPages`, and caches hold complete collections or single pages, never a partial collection as complete. Every call makes progress, so the browser's "made no progress" guard never trips on large data: each finishes or advances its first unit, using the retry headroom if it must. Failed reads fail the call as typed faults and the browser offers Retry; nothing is swallowed into empty data.

- **People dashboard.** `people.dashboardRoster` (one `teams?include=people` read), then `people.dashboardActivity` for 16 people per call: one schedule page each (two at most), then one plan-range read per service type with rehearsal times, first the service types of the call's first person. That person always finishes; past the cap (more than about ten service types), their remaining schedules keep their plan dates without rehearsal times. The browser renders the roster at once and fills in each batch as it answers, two calls at a time; a search matches the whole scope and loads unloaded matches one call at a time, ahead of sample batches not yet started.
- **Person detail.** `people.dashboardPerson` is a POST read within the same budget. It reads the person's schedules (declined included) over the dashboard's 181-day window and resolves rehearsal times over the same 91 days, so its `rhythm` matches the dashboard's for the same person: plan ranges go to the service types missing the most rehearsal times while leaving room for plan-by-plan reads. Plan pages that do not fit come back as `continuation` (the plans' next offsets and the times found so far); the browser passes it back until it is `null`, and only complete details are cached. More missing times than that continuation accepts fail the read typed (`cursor-limit`). Times Planning Center does not list on their plan keep their plan date, `requestBudget.unresolvedRehearsalTimes` counts them, and the detail view says so under the month's commitments.
- **Assign view candidate list.** Three procedures (`modules/planning-center/get-position-candidates.ts`, `get-plan-window-history.ts`, `get-candidate-details.ts`) whose results the browser assembles with `assemblePositionCandidates` from `@pcobooster/planning-center-models/position-candidates`, the same code for every client and test:
  - `people.positionCandidates`: the position's assignments and the selected plan's roster, read through its own 30-second cache (`getPlanTeamMembers`) so slot statuses are fresh. About 3 requests cold.
  - `people.planWindowHistory`: the roster of every plan within 28 days of the plan date, across active service types (plus plans up to a week later whose rehearsal falls inside the window), read in window order until the budget runs out, continued with `deferredPlans` and `deferredRanges`. Each service type's plans are listed a range page (100 plans, date order, cached per page) at a time until a page passes the window, so a window of any size is read to its end; `deferredRanges` holds where each range goes on: the position of the last plan listed and its id (`boundaryPlanId`), which the next page must start with. Deferred plans carry their roster pages and the range page that listed them, so a follow-up call finds each again on that page (or a neighboring one, if plans moved), reserves the first one's roster, and always reads it, using the retry headroom up to the procedure cap when it must. Planning Center offers only offsets in `sort_date` order, so when a range no longer starts at its boundary plan or a deferred plan is on none of its pages, plans were added, deleted, or moved under the read: the call fails typed (`PlanningCenterPaginationError`, `changed`) and the browser's retry reads the window again from the start, rather than skip or repeat plans. This assumes Planning Center lists unchanged plans in the same order each time, ties included; its documentation orders by `sort_date` alone. A cursor never holds more ranges than the catalog's service types (`MAX_SERVICE_TYPES`; more fail the catalog read) or more deferred plans than it accepts. It returns compact roster rows plus the plans and plan times they point at; the browser expands them into history items. It depends only on the date, so every position and plan on that date shares one browser query. Window rosters (`getPlanWindowRoster`) have their own cache, 5 minutes per plan (30 for plans that already happened), so they never stand in for the fresh selected-plan roster; schedule writes clear the plan's copies, and plan time writes clear the account's window rosters. Clients call it once per active service type (`serviceTypeId`), all at once, each following its own continuation (`readPlanWindowHistory` in `@pcobooster/planning-center-models/candidate-list`). One invocation holds six Planning Center connections, so the window takes about as long as its busiest service type rather than every roster in turn (about 1.1 s instead of 2 s for 36 rosters across 7 service types).
  - `people.candidateDetails`: whether a blockout covers the plan date, for up to 16 candidates, continued with `deferredPersonIds`. Each person costs a request per page actually needed: their blockout list, and the `blockout_dates` pages of each repeating blockout that may reach the plan date, stopping at the first page with a date that covers the day. A person whose pages do not fit in one call is checked across calls: `continuation` carries their next list page, the repeating blockouts still being read with their next date page, and whether one covered the day; nobody counts as available until every page is read. When the window has no plans at all, the browser asks it for each person's own schedules too (`scheduleHistory: true`), read with `filter=after` from the window start, because Planning Center's default schedule scope is upcoming only. Every schedule page from the window start is read (more than ten pages fails the call): Planning Center orders schedules by `starts_at` while history dates them by `sort_date` and their times, so no page's dates prove the rest hold nothing history or the selected plan needs, and history keeps every schedule read. Their rehearsal times are read plan by plan, page by page (cached per page and shared by everyone on the plan), for every plan in the window, across calls when they do not fit, stopping once a plan's missing times are found; the cursor carries the times found until the person is complete, so a person whose rehearsal plans list more times or plans than it accepts (`MAX_PROGRESS_TIMES`, `MAX_PROGRESS_PLANS`) fails the call typed (`cursor-limit`) before their plans are read. A blockout list page is read only while the cursor can hold the repeating blockouts it may add.

  Scores are normalized across available candidates, so they exist only once every part has arrived. The browser holds the list's skeleton for up to 1.5 seconds after the candidates arrive, so a list that scores in that time appears already sorted; past that it shows in a stable order with score placeholders and sorts once when the scores land. `position-candidates-equivalence.test.ts` pins the assembled result to the output of the single-call `people.list` it replaced.

## Planning Center read caches

Planning Center reads are cached in two tiers, both keyed by the client's cache scope: `<auth kind>:<sha256 of the credential>`, never the credential itself.

- **Memory** (`PlanningCenterReadCache`): one set per isolate (`PlanningCenterReadCaches`), created with `ServerDependencies` and passed to the services factory; the plan window rosters live there too. Loaded values are shared by every request the isolate serves, but a request only joins loads it started: `ProcedureScope` gives each procedure its own view (`serverDependenciesForRequest`, which calls `forRequest` on every cache), and concurrent loads coalesce within that view with per-caller waiters. workerd ties I/O to the request that started it, so a request awaiting another request's load would never settle once that request ended or was cancelled (`read-cache.workerd.test.ts` reproduces it). Concurrent misses for one key in different requests therefore each load (more Planning Center requests during bursts, but never more than the request would spend loading the key itself); once a load finishes, every request reads its value. Mutations invalidate through `deleteWhere`, which also marks loads still running in other requests stale, so their callers load again. Other isolates keep their own copies until the TTL. Caches of values that feature modules derive from those reads live in a second per-isolate set, `ModuleReadCaches` (`modules/read-caches.ts`), created with `ServerDependencies` next to the service caches so the services never depend on module types. Application programs read it from the `Server` service and pass each module its cache as a dependency: the People dashboard person page (2 minutes), the demo organization (10 minutes), the presentation-mode organization id (5 minutes), and ranked song search results (5 minutes). The organization time zone cache (1 hour, or 2 minutes for the configured fallback) belongs to the service caches, and the services factory exposes the resolved zone as `services.organizationTimeZone`. Tests pass fresh caches (`createPlanningCenterReadCaches(null)`, `createModuleReadCaches()`, or `testServer()`), so no test shares cache state with another.

  No cache lives at module scope. `lint/architecture-boundaries.test.ts` fails when code under `packages/api/src/modules` or `packages/api/src/planning-center` creates a `Map`, `WeakMap`, or `PlanningCenterReadCache`, or a `let` binding, at module scope, outside a short, justified exception list (empty today); factories that build caches when called are fine. Two isolate-wide pieces of state remain outside those roots on purpose: the `PlanningCenterRatePacer` the Worker builds once per isolate (see Pacing above), and the local-only dev bypass identity (`auth/dev-bypass.ts`), which caches the one identity behind `ServerConfig.localPlanningCenterToken` and never runs outside the local stage.

- **Shared** (`shared-read-store.ts`): a Workers KV namespace per stage (`apps/server/src/planning-center-cache.ts`), bound in `worker.ts` and passed in as a `SharedReadStore`. On a memory miss, a shared cache reads KV before Planning Center and stores what it loads. Store keys are `pc1:<scope>:<cache>:<sha256 of the cache key>`, and a cache key outside its scope is rejected. Values go through a per-cache codec that validates them on the way back, so a malformed entry is a miss.

A cache uses the shared tier only when both hold (`bindReadCaches` in `factory.ts`):

- **No mutation in this app invalidates it.** KV cannot be invalidated reliably across isolates and locations: it is eventually consistent, allows one write per second per key, and on Workers Free allows 1,000 writes a day. A shared cache refuses `deleteWhere`, and a test calls every mutation invalidation with the shared tier on. Its data changes only in Planning Center itself, so the shared tier serves it no staler than the memory tier would: each entry keeps the original load's expiry.
- **A KV hit saves more Planning Center requests than it costs.** KV calls consume internal-service subrequests, separate from Free's 50 external requests; on the current Paid account they count against the configured Worker limit. A memory miss costs one KV read, plus one KV write when KV misses too.

That leaves two caches: the team people directory (the teams list plus one request per team) and the song catalog (one request per hundred songs, read six at a time after the first). Service types were dropped, because a KV read would replace a single request, and a miss would cost three subrequests instead of one. The song catalog is cached per credential rather than per service type, since Planning Center's catalog belongs to the organization, and for an hour. Library, search, and suggestions first read a D1 revision for that credential scope; creating a song advances it before the follow-up arrangement work, so in-memory, ranked-search, and shared KV entries from before the write cannot answer later requests. Concurrent creates increment it atomically. Mutable song details, arrangements, and history are read directly from Planning Center, since a write can land in another Worker.

The shared tier never fails a request. A KV error or quota rejection is logged at `warn`, the read falls back to Planning Center, and the isolate stops using that half of KV (reads or writes) for 15 minutes. workerd ties I/O to the request that started it, so each request's services own a shared-tier session, and its writes are awaited before the response: the `PlanningCenterSession` middleware (`packages/api/src/http/planning-center-session.ts`), `withPlanningCenterAccess`, and demo organization loading release the services with `settleReadCaches` through `Effect.acquireUseRelease`.

Historical Free-tier cache sizing ([KV limits](https://developers.cloudflare.com/kv/platform/limits/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)):

- **Writes (1,000 a day):** only a KV miss writes, at most once per scope and key per TTL window across all isolates. With a 5-minute team directory and a 1-hour song catalog, one continuously active scope writes at most 13 times an hour, so the quota covers about 75 fully active scope-hours a day. A scope changes whenever the user's access token does (every 2 hours for OAuth). Past the quota, writes stop and reads come from Planning Center.
- **Reads (100,000 a day):** at most one per shared cache on a memory miss, so at most two per request.
- **Subrequests:** at most two extra per shared cache in a request. A team directory hit replaces 1 + T requests (13 for 12 teams); a song catalog hit replaces about 10 pages (about 1 s read in parallel).

The Cache API was rejected: Alchemy's `Cloudflare.cache()` is Workers Cache for a Worker's own HTTP responses (API responses are `private, no-store`), and `caches.default` is per location, only works for Workers on a custom domain (this Worker is reached only through service bindings), and also counts toward the subrequest limit. The current Workers Paid account could support a broader shared tier if mutations published invalidation markers; that is a separate design change.

## Migration invariants

Each migration layer owns a complete vertical slice: contract, application program, endpoint, web caller, tests, and deletion of the replaced route. Do not leave a second business implementation behind as a compatibility path. Better Auth routes, liveness health checks, and the iOS over-the-air update routes (`packages/api/src/http/mobile-updates.ts`, fixed by the Expo Updates protocol) are the only intentional HTTP surfaces outside `/api/v1`.
